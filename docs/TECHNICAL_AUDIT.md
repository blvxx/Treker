# Техническая ревизия «Вдох»

Дата ревизии: 2026-11-21  
Основа объединения: `blvxx/Treker`  
Второй исходный репозиторий: `blvxx/HabitForge`

## 1. Состояние репозиториев

### Treker

- Default branch: `main`.
- Текущая реализация: один файл `index.html` (около 81 КБ, 1 354 строки) и `README.md`.
- Стек: нативные HTML, CSS и JavaScript; один встроенный блок стилей и один встроенный скрипт.
- Внешние JS/CSS-библиотеки не подключены. Google Fonts загружаются извне.
- Приложение запускается открытием `index.html` в современном браузере; сборка не требуется.
- Данные сохраняются в браузере через `localStorage`, ключ `vdoh.v1`.
- Есть экспорт состояния в JSON, но нет серверной синхронизации, аккаунтов или восстановления данных между устройствами.

Реализованные возможности, подтверждённые кодом:

- таймер с момента последней сигареты;
- этапы/временная шкала отказа;
- оценка количества невыкуренных сигарет и сэкономленных денег;
- пользовательские параметры (дата, количество сигарет, стоимость пачки, валюта);
- журнал тяги с интенсивностью, заметками, поиском, фильтрами и графиком;
- дыхательный таймер с несколькими шаблонами;
- визуализация лёгких на Canvas;
- звук через Web Audio;
- экспорт и сброс локальных данных;
- адаптивные стили и поддержка prefers-reduced-motion.

### HabitForge

- Default branch: `main`.
- Репозиторий содержит только `README.md`.
- Рабочей реализации, исходников интерфейса, тестов и зависимостей нет.
- README перечисляет концептуальные функции трекера привычек: ежедневный список, серии, прогресс, локальное хранение, адаптивный интерфейс.

Вывод: переносить из HabitForge исходный код нечего. Его продуктовую идею и перечень функций включаем в единый «Вдох». Исходный репозиторий пока не удаляем и не изменяем.

## 2. Решение по объединению

Использовать Treker как исходную точку и сохранить его текущий интерфейс/функциональность в истории Git. Новую архитектуру вводить постепенно, небольшими проверяемыми изменениями. Не переписывать весь HTML-файл одним большим коммитом.

Текущая рабочая ветка подготовки: `feature/vdoh-foundation`. Основная ветка `main` не изменялась.

## 3. Технические ограничения текущей реализации

1. Монолитный HTML-файл смешивает разметку, стили, состояние и бизнес-логику.
2. Состояние привязано к одному браузеру и одному устройству.
3. Начальное состояние может включать демонстрационные записи; их нужно визуально отделять от реальных данных и не смешивать с пользовательской историей.
4. Нет аккаунтов, backend API, базы данных, синхронизации и управления сессиями.
5. Интерфейс только на русском: `lang="ru"`, русские подписи и форматирование.
6. Нет автоматизированных тестов, CI и зафиксированных критериев приёмки.
7. Встроенные тексты о сроках восстановления и влиянии отказа от курения требуют проверки по надёжным медицинским источникам и редакционной оговорки. Визуальный индикатор не должен изображать медицинское измерение или гарантированный темп восстановления.
8. Дыхательные шаблоны должны иметь безопасные настройки по умолчанию и возможность немедленно остановить упражнение. Не позиционировать практики как лечение.
9. Все динамические данные, включая заметки пользователя, должны безопасно выводиться в DOM. Существующую функцию экранирования сохранить и покрыть тестами; новые шаблоны не должны вставлять пользовательский ввод как HTML.
10. Ошибки сохранения в localStorage сейчас подавляются. В будущем показывать понятный статус, если сохранение не удалось.

## 4. Что сохраняем

- Текущую реализацию Treker как исторический baseline.
- Функции журнала тяги, таймера, настроек, экспорта и дыхательного интерфейса.
- Визуальные наработки и адаптивную структуру, если они проходят проверку доступности.
- Историю Git и исходный репозиторий HabitForge.

## 5. Что не считаем реализованным

Следующие функции пока являются целями разработки, а не существующими возможностями:

- трекер полезных привычек;
- полноценные программы отказа от разных вредных привычек;
- планы тренировок и история занятий;
- дневник питания, рецепты и список покупок;
- AI-помощник и персональные рекомендации;
- Telegram-бот и уведомления;
- backend, PostgreSQL, аккаунты и синхронизация;
- полноценные web/mobile клиенты;
- английская локализация.

## 6. Рекомендуемый порядок рефакторинга

1. Зафиксировать текущее поведение ручными тест-кейсами.
2. Добавить базовые автоматические проверки и CI.
3. Разделить монолит на модули без изменения поведения.
4. Ввести типизированные модели данных и слой хранения с миграцией старого состояния `vdoh.v1`.
5. Реализовать модуль привычек.
6. После стабилизации UX выделить backend API и синхронизацию.
7. Затем подключать мобильный клиент, AI и Telegram.

## 7. Проверка безопасности и приватности

Первый релиз предназначен для личного использования. Тем не менее с самого начала не помещать API-ключи и секреты в frontend или Git. Персональные данные должны быть минимизированы, экспортируемы и удаляемы. Перед подключением AI явно определить, какие данные могут передаваться внешнему AI-провайдеру, и запрашивать согласие пользователя.
