# Техническая ревизия «Вдох»

Дата ревизии: 2026-11-21  
Основа функциональных наработок: `blvxx/Treker`  
Второй исходный репозиторий: `blvxx/HabitForge`  
Целевая платформа продукта: Android mobile app

## 1. Состояние исходных репозиториев

### Treker

- Default branch: `main`.
- Текущая реализация: один файл `index.html` (около 81 КБ, 1 354 строки) и `README.md`.
- Стек: нативные HTML, CSS и JavaScript; встроенные стили и скрипт.
- Внешних JS/CSS-библиотек нет; Google Fonts загружаются извне.
- Запускается в браузере без сборки.
- Данные сохраняются через `localStorage`, ключ `vdoh.v1`.
- Есть экспорт JSON, но нет аккаунтов, backend или синхронизации между устройствами.

Подтверждённые функции:
- таймер с момента отказа от курения и временные этапы;
- ориентировочная статистика невыкуренных сигарет и экономии;
- параметры даты отказа, потребления, стоимости пачки и валюты;
- журнал тяги с интенсивностью, заметками, поиском, фильтрами и графиком;
- дыхательный таймер с несколькими шаблонами;
- визуализация лёгких на Canvas;
- звук через Web Audio;
- экспорт и сброс локальных данных;
- адаптивные стили и prefers-reduced-motion.

### HabitForge

- Default branch: `main`.
- Репозиторий содержит только `README.md`.
- Рабочей реализации, исходников, тестов и зависимостей нет.
- README описывает идею трекера привычек: ежедневный список, серии, прогресс, локальное хранение и адаптивный интерфейс.

Вывод: исходный код переносить из HabitForge не требуется. Его концепцию реализуем как модуль мобильного приложения «Вдох». Оригинальный репозиторий пока не удаляем и не изменяем.

## 2. Новое продуктовое решение

Основной продукт — Android-приложение с последующей публикацией в Google Play. Сначала private testing и личное использование. Русский и английский языки — с первого этапа.

- Основной UI: React Native + Expo + TypeScript.
- Локальное хранилище: SQLite через Expo SQLite, с offline-first подходом.
- Backend: Python + FastAPI.
- Серверная БД: PostgreSQL.
- AI: серверный gateway, ключи AI-провайдера не попадают в приложение.
- Telegram: дополнительный канал уведомлений и быстрых действий.
- iOS — возможное будущее расширение, не обязательная часть первого релиза.
- Отдельный web-клиент не входит в текущий план.

## 3. Как использовать Treker

Браузерный HTML/CSS нельзя напрямую считать основой Android UI на React Native. Treker сохраняется как:
1. рабочий reference для существующих сценариев;
2. источник проверенной продуктовой логики, которую можно выделить и перенести в TypeScript;
3. baseline для ручных regression-тестов;
4. резервная версия до завершения мобильного переноса.

Не переписывать весь HTML-файл в React Native механически. Сначала зафиксировать поведение, затем извлечь и протестировать доменные расчёты и правила, после чего реализовать мобильные экраны нативными компонентами React Native.

## 4. Технические ограничения текущей реализации

1. Монолитный HTML смешивает разметку, стили, состояние и бизнес-логику.
2. Данные привязаны к одному браузеру и одному устройству.
3. Начальное состояние может включать демонстрационные записи.
4. Нет аккаунтов, backend API, базы данных, синхронизации и управления сессиями.
5. Интерфейс только на русском.
6. Нет автоматизированных тестов и CI.
7. Информационные тексты о восстановлении организма требуют проверки по надёжным медицинским источникам; визуальные индикаторы не должны изображать медицинские измерения.
8. Дыхательные шаблоны должны иметь безопасные настройки и немедленную остановку.
9. Пользовательские заметки должны выводиться безопасно; существующее экранирование покрыть тестами.
10. Ошибки localStorage сейчас подавляются; мобильное хранилище должно иметь явную обработку ошибок и резервный экспорт.
11. Локальные данные старого Treker должны переноситься через контролируемый импорт/миграцию, а не удаляться при установке нового приложения.

## 5. Что сохраняем

- Исходную реализацию Treker и историю Git.
- Функциональные сценарии журнала тяги, таймера, настроек, экспорта и дыхательных упражнений.
- Продуктовую логику после проверки и выделения в тестируемые TypeScript-модули.
- HabitForge как исходный продуктовый brief.

## 6. Что ещё не реализовано

- Нативное Android-приложение;
- полезные привычки;
- полноценные программы отказа от разных привычек;
- тренировки и история занятий;
- дневник питания и рецепты;
- AI-помощник;
- Telegram-бот;
- backend, PostgreSQL, аккаунты и синхронизация;
- английская локализация;
- сборка AAB, подпись, Play Store listing и публикация в Google Play.

## 7. Следующий технический порядок

1. Зафиксировать baseline-сценарии Treker.
2. Подготовить тесты доменной логики.
3. Создать Expo + React Native + TypeScript Android app.
4. Настроить ru/en, навигацию, дизайн-систему и SQLite.
5. Перенести Recovery и Breathe в мобильный интерфейс.
6. Добавить Habits.
7. Добавить Android regression/E2E и CI.
8. После полезного offline MVP подключить backend, синхронизацию, AI, Fitness, Nutrition и Telegram.

## 8. Безопасность и приватность

Не помещать API-ключи и signing keys в приложение или Git. Персональные данные минимизировать, сделать экспортируемыми и удаляемыми. Перед передачей контекста AI-провайдеру запрашивать согласие. Уведомления по умолчанию не должны раскрывать чувствительные подробности.
